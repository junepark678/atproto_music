# M6 contract reconciliation proposal — review only

**Status: draft / owner review required / not published.** This note proposes how to reconcile M6 issues #98–109 with the Node-host direction in ADR 0005. It does not amend ADRs, OpenAPI, runtime behavior, GitHub issue text or state; it does not close issues or authorize a release/deployment. The published issue bodies remain authoritative until their owners approve and publish amendments. M7 remains excluded.

## Purpose and evidence boundary

The [M6 audit](m6-audit.md) records meaningful Node fixture, recovery, packaging, backup/restore, and installer-safety evidence. It also records specific differences between the published Rust/Workers-era acceptance text and the current Node architecture. A passing local test or case-map validator is not semantic approval of those differences. The [deployment plan](m6-deployment-plan.md) remains **NO-GO**: there is no approved clean artifact, verified production backup, rehearsed rollback, complete target/owner confirmation, or accepted live evidence.

This proposal is intended to turn the known differences into explicit owner decisions. It is not based on inspecting credential contents or changing production/GitHub state. It does not treat the active tunnel as proof of target ownership, readiness, or authorization.

## Suggested owner sequence

1. **Confirm product/release direction:** explicitly reconcile the published Rust/static-artifact requirements with ADR 0005's Node host. Decide M6 asset scope without pulling M7 into this proposal.
2. **Resolve externally visible/privacy-sensitive contracts:** choose the #101 limit table, #105 export authorization, and #106 disconnect/data-removal semantics. Update OpenAPI, operator/user docs, tests, and the semantic case map only after approval.
3. **Accept operational semantics:** confirm #102 observability, #103 benchmark/attestation, and #104 restore/revocation behavior. Preserve candidate-bound verification and recovery requirements.
4. **Approve the release and deployment protocol:** define the artifact/provenance identity, exact archive contents, installer/activation/health/rollback path, target ownership, backup/restore proof, and maintenance impact. Keep a first install NO-GO until the owner verifies alternate state locations and recovery.
5. **Only then update GitHub issues:** publish approved amendments without closing issues; update the local contract mirror, OpenAPI/docs, test case map, and acceptance inventory together. Record hosted and live evidence separately from fixture tests.

## Non-negotiable evidence distinctions

- Local deterministic tests and dirty-tree receipts are not hosted CI, an approved release, or production acceptance.
- A package/checksum is not trusted provenance; a staged symlink is not installation or activation; an installer fixture is not a real service restart.
- A backup test is not a verified production backup or restore rehearsal.
- DNS ownership evidence is not schema publication; keep the write/publication gate closed until approved schemas and their public retrieval are verified.
- A successful readiness probe would not establish OAuth, federation, privacy, recovery, or soak acceptance. Current bounded probe results remain unhealthy.
- No credential contents, GitHub issue state, production configuration, service, tunnel, namespace record, or database may be changed as part of this proposal.

## Current disposition

All **12** M6 issues remain **OPEN**. This proposal does not make M6 closure-ready and does not reduce the gates in the [NO-GO deployment plan](m6-deployment-plan.md). Owner decisions and an approved artifact/target are still required before any production mutation.
