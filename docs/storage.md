# SQLite storage contract

The application keeps one database file in its configured data directory. SQLite is a single-instance database: one dedicated transactional writer and a maximum of four pooled readers. Every connection enables foreign keys, WAL and a 5,000 ms busy timeout. The writer channel has exactly 1,024 waiting commands; full admission returns `service_busy` immediately. A command receives its acknowledgement after its transaction commits. A lock held beyond the timeout returns `storage_busy`; its transaction rolls back. Shutdown closes admission under a mutex and drains all accepted commands.

The four forward SQLx migrations are embedded using `include_str!`; no migration files are required beside the binary. SQLx records migration versions/checksums in `_sqlx_migrations`; `PRAGMA user_version` records the supported application schema, currently 4. Migration 2 adds operation dependencies, migration 3 adds durable backfill and relay recovery state, and migration 4 adds a service-wide backfill generation allocator. Before enabling WAL, opening an existing file uses a read-only connection and rejects either version above the supported schema with `schema_too_new`. No downgrade is attempted. SQLx executes each migration in a transaction. Failed migrations leave both the schema and the recorded version unchanged. A successful reopen preserves rows and does not replay applied migrations.

## Tables and columns

`TEXT` timestamps in public tables are canonical UTC RFC3339 with nine fractional digits. This makes SQLite textual comparisons equivalent to instant comparisons, including sub-microsecond precision. Private expiry timestamps are `INTEGER` Unix seconds. Identifiers, grouping values, CID/revision evidence, collection names and record keys are `TEXT`; encrypted envelopes are `BLOB`. Booleans are checked `INTEGER` 0/1. Optional values are SQL `NULL`.

| Table | Columns and invariant |
| --- | --- |
| `users` | `did` primary key; nullable uniquely verified `handle`; `joined_at`, nullable `indexed_at`; checked `active`; nullable `revision`; checked `indexing_state` current/recovering/stale/suppressed. Existing users retain their first joined timestamp. |
| `scrobbles` | `uri` primary key; `cid`, owner `did` foreign key, `revision`; artist/track, nullable album; listened/created/indexed timestamps; nullable duration constrained 1–86,400 and MBID; normalized `artist_key`, `track_key`, nullable `album_key`; checked `confirmed`. Artist/track/album grouping uses separate columns, never concatenated identity strings. |
| `follows` | `uri` primary key; CID; owner `actor` foreign key; `subject` DID; revision; created/indexed timestamps; checked confirmed. Self follows are rejected. Duplicate external actor/subject records are permitted and public reads select the lexicographically smallest active URI representative. |
| `operations` | opaque `operation_id` primary key; owner foreign key; checked kind scrobble/follow create/delete; checked state pending/succeeded/failed; attempts 0–10; created/updated timestamps; nullable `record_uri`, sanitized nullable `failure_code`. Success cannot retain a failure code. |
| `outbox` | operation foreign-key primary key; owner foreign key; collection and persistently allocated rkey; nullable canonical JSON/digest pair; due timestamp; nullable locked timestamp. Payload and digest must both exist or both be absent (deletion). |

| `suppression` | disconnected DID primary key and suppressed timestamp. It intentionally survives deletion of the user and blocks incoming repository records until fresh authorization and reconciliation. |

User foreign keys cascade local disconnect into public records, secrets, sessions, operations, outbox and idempotency. Tombstone operation references become null on operation deletion. Follow subjects need not be locally known, so subject is not a foreign key. Suppression likewise has no user foreign key.

Indexes support per-owner/global `(listened_at DESC,uri DESC)` traversal, owner/statistic grouping, actor/subject and subject/actor edge lookup, owner operation status, due outbox work, session owner/expiry and verified handle lookup. Public query predicates require confirmed records, active owners, no tombstone and no suppression; inactive or disconnected users do not remain visible through feeds or follow counts.

## Repository boundary

`Database::repositories()` returns the typed repository. Server and protocol modules do not issue SQL. Repository application methods consume already verified and schema-valid CID/revision evidence from the protocol boundary; SQLite is not a signature verifier. Pending operation admission never inserts confirmed scrobbles or follows. Terminal create success requires independently confirmed record state. The protocol caller must perform signature, CID, membership and schema validation before `apply_event`, `apply_scrobble` or `apply_follow`.

Replaying the same record revision is a no-op. Older revisions cannot replace newer payloads or resurrect a revision-protected deletion. Replaying an already applied relay sequence is a no-op. `apply_repository_event` advances the verified commit's owner revision even for follow-only, nonmusic or excluded-record commits, independently of whether a visible row changed. Projected owner/revision pairs must match that commit. Record changes, owner revision and checkpoint advancement commit together; any failure rolls them all back. Generic `apply_event` remains available for typed compatibility fixtures. Owner-bound private operation reads return no row to a different owner. A separate authenticated existence check supports the API's required 403/404 distinction without exposing private operation content.

Cursor upper bounds are inclusive and last-seen bounds exclusive over the full timestamp/URI tuple. These are current-record reads, with deletion/update visibility rather than historical snapshot isolation. Arrival above an existing traversal anchor waits for a fresh traversal.

`Database::close` waits for accepted transactions, then the writer's actual connection close, then the reader pool. `Writer::drain` retains its transaction completion semantics for the bounded graceful shutdown coordinator. A returned database close cannot leave an owned writer racing later WAL checkpoint/file reads.

Account export pins one SQLite read transaction across owner lookup, scoped indexing metadata, durable pending backfills, configured relay recovery state and all owner public records. Lag uses the injected export timestamp; there is no post-snapshot freshness reread. It emits schemaVersion 1 as a no-store JSON attachment and never queries OAuth, session or operation material. Local disconnect atomically persists suppression and removes owned rows, secrets, sessions and queued work without contacting the PDS. Other owners' incoming follow records remain owned by those users and are hidden while their subject is suppressed. Only a verified fresh OAuth callback clears suppression, installs new encrypted material and queues backfill in one transaction. Reactivation waits for a complete signed snapshot; ordinary recovery rescheduling preserves pending authorization to reactivate, while explicit account deactivation clears it. Ordinary token initialization rejects suppression; refresh replacement compares the original generation and ciphertext, preventing both post-disconnect resurrection and stale replacement after reconnect.

Backfill admissions and invalidations allocate monotonically increasing generations in the same writer transaction. The global counter contains no DID or account data and survives disconnect; recreated jobs cannot reuse an old generation. Account-status completion checks the captured generation, user existence and suppression atomically before deactivation or reactivation admission. Exhaustion fails and rolls back instead of allowing SQLite integer arithmetic to promote to floating point. API, export and lexicon schema versions remain 1.

## Encrypted OAuth and durable publishing

OAuth state and token material use maintained AES-256-GCM with a fresh operating-system nonce on every write. The configured 32-byte application key derives separate state/token encryption keys through HKDF-SHA256. Authenticated associated data binds the envelope version, purpose, owner/state hash and issuer; swapping ciphertext between owners or issuers fails authentication. Tokens, refresh tokens, PKCE verifiers and DPoP private keys stay inside authenticated ciphertext. Refresh locks are bounded to 1,024 concurrent DID entries and cleaned when unused. Under the lock, refresh re-reads persisted expiry, exchanges once, and atomically replaces the whole rotated envelope. `invalid_grant` removes usable tokens and every session only if the original encrypted material remains current. A stale success, invalid-grant or revocation completion cannot replace or invalidate fresh authorization. PAR nonce updates preserve the original state expiry. Revocation and refresh share the same DID lock.

Admission distinguishes the digest of canonical local input (the durable replay/conflict key) from the digest of the full canonical AT record (remote recovery evidence). `admit_scrobble_factory` checks replay/conflict inside the writer transaction before allocating any operation ID or TID; the factory executes once for a new request. Operation, outbox, record identity and replay key commit together. Scrobble TIDs use pinned `atrium-api` encoding and a serialized monotonic microsecond allocator; persisted identities are reused after restart.

The outbox worker persists each attempt before sending. Transport failures, HTTP 429 and server errors schedule exponential base 1s, 2s, 4s, … with uniform jitter up to one quarter of the base; the whole delay is capped at 300s. Retry-After can raise that delay to the cap. Exactly ten total attempts are permitted. After the cap, crash recovery may issue a read-only reconciliation but cannot issue an eleventh write. Permanent record/scope errors end the operation. A rejected access token permits one supported refresh recovery.

The PDS boundary checks owner/collection/rkey against independently verified signed repository state, sends DPoP-authorized create/delete requests, and confirms through a separate getRecord plus signed getRepo CAR. A create response's CID alone cannot confirm a public row. Unknown create outcomes first reconcile the persisted identity and compare the full canonical record digest; conflicting records are never overwritten. Signature/CID/MST verification and exact current-head DID/revision/CID evidence remain mandatory. Owned-namespace startup installs this resolver; a missing key or invalid witness fails closed, while head movement retries within the outbox's bounds. A pending local deletion keeps any subsequently confirmed create hidden until the verified deletion finishes; it does not prevent durable remote confirmation of the create operation itself.
