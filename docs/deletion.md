# Deletion semantics

`DELETE /api/v1/scrobbles/{uri}` takes a percent-encoded full AT URI. It requires an authenticated owner session, the configured Origin, and its CSRF token. A different owner's URI returns 403 without changing visibility or contacting the PDS. Production deletion requires an owned namespace and an initialized verified PDS outbox; unavailable capability returns 503 before admission.

Deletion admission commits a tombstone and durable operation in one SQLite transaction. History, lookup, feeds, and statistics stop exposing the scrobble immediately. A missing local row still returns 202 with a pending operation: local absence does not establish PDS absence. Repeating a pending request returns the same operation. After signed absence is confirmed, repetition returns 204.

A never-sent create is cancelled atomically and deletion returns 204, because no worker has begun publication. When a create has begun an attempt, the delete depends on that create's terminal reconciliation. Dependencies survive restart, and the delete cannot run ahead of an ambiguous create. A late verified create can be recorded behind the tombstone while remaining hidden.

Deletion sends the CID from the verified current record as `swapRecord`. A concurrent record change causes `InvalidSwap`, retains the tombstone, and retries from fresh signed evidence. PDS success responses and `RecordNotFound` are candidates for reconciliation. Completion requires a trusted DID signing key and a valid signed CAR, commit, and MST absence proof for the persisted record identity. A restart after remote deletion reconciles the same durable operation without another delete request when signed absence is already present. Transient failures retain the tombstone and retry schedule. Permanent failure leaves the record hidden and the owner operation failed; repeated DELETE returns 502 with its operation in `Location`, without claiming remote deletion.

`server/tests/deletion.rs` executes the nine M3.3 named cases using the full router over port-0 HTTP, session/CSRF checks, a port-0 PDS HTTP fixture, the production PDS client and verifier, and deterministic signed repositories. It additionally checks stale-CID races, authentication and URI validation, unverified absence/acknowledgement, and unavailable worker behavior. `storage/tests/deletion_views.rs` checks the typed projection transaction boundary. These automated controlled fixtures do not substitute for the milestone's external live PDS evidence gate.
