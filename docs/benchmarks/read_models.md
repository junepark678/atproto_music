## Dataset (M6.2.3 `benchmark_dataset`)

100 users × 1,000 scrobbles = 100,000 active rows, generator seed 7, frozen clock 2026-01-15T12:00:00Z. Each repository is a real signed commit (deterministic fixture keys); its signature is checked with the production `verifyCommit` (100 commits), its MST is walked by the production range walker in chunks of at most 2,000 entries (100 chunks, the largest 1,000 entries), and every chunk goes through the production `applySnapshotChunk` and `completeSnapshot` (0 exclusions). Per user: 100 artists × 10, 500 tracks × 2, 50 albums × 20, one listen every 60 s, durations 120–419 s from the seeded generator. Row digest (SHA-256) `561cf834ad47974bc3fe6c26f2d629ae0429c0a099b0fc34c2853d25ab4b552d`. Seeding took 19,003 ms.

## Query plans (ADR 0005 §15.3 (ADR 0004 §15 Q10 re-derived as query plans)), SQLite 3.54.1

node:sqlite reports no rows read, so the ADR 0004 §15 Q10 rows-read budgets are re-derived as EXPLAIN QUERY PLAN pins on the SQLite the Node host runs: a deep page must carry the keyset bound on its index range and seek from the cursor's last row (checked in the EXPLAIN bytecode, which catches the O(depth) anchor-keyed seek W6-02 found), and a bounded statistics window must read scrobbles only through a search bounded by both window ends (which catches the DID-only `scrobbles_stats` search W6-02 found). They are hard assertions in `the read-model bench records p50 and p95 for history, feed and stats on node:sqlite and asserts their query plans`; timings are reported, never asserted.

| Read | Required plan |
| --- | --- |
| History | SEARCH scrobbles_owner_time (did=?), no SCAN, no temporary B-tree; a deep page's search is bounded by (listened_at,uri)<(?,?) and seeks from the cursor's last row; delete visibility SEARCHes operations_scrobble_delete_target by did and rkey |
| Global feed | scrobbles_global_time in order, no SCAN, no temporary B-tree; a deep page's search is bounded by (listened_at,uri)<(?,?) and seeks from the cursor's last row; delete visibility SEARCHes operations_scrobble_delete_target by did and rkey |
| Following feed | SEARCH scrobbles_owner_time per followee and follows_actor_subject, no SCAN; a deep page's search is bounded by (listened_at,uri)<(?,?) and seeks from the cursor's last row; delete visibility SEARCHes operations_scrobble_delete_target by did and rkey |
| Statistics (uncached) | every scrobbles statement SEARCHes scrobbles_owner_time or scrobbles_stats by DID, no SCAN; in a 7d, 30d or 365d window every scrobbles SEARCH is bounded by did=? AND listened_at>? AND listened_at<?; delete visibility SEARCHes operations_scrobble_delete_target by did and rkey |
| Statistics (cached hit) | at most 4 indexed probes for a window, 3 for `all` |

Met: all 12 history and feed page statements plan as required.

## Follow-ups

- `worst-following-sparse-followees-first`: Following feed, first page: the viewer follows only 3 accounts with 20 listens each, spread over two years of a 20,060-row visible timeline. p50 0.464 ms, p95 0.725 ms for 20 rows (the dense first page of this kind of read: p50 0.353 ms; scrobbles plan: SEARCH s USING INDEX scrobbles_owner_time (did=?); USE TEMP B-TREE FOR ORDER BY). SQLite walks each followee's scrobbles_owner_time range (up to L + 1 rows each) and merges the walks in a temporary B-tree, so the cost grows with the number of followees, not with the size of the global timeline. Measured and reported, not asserted (Q10). (measured 0.46, threshold 0.35)
- `worst-following-sparse-followees-deep`: Following feed, deep page (depth 30): the viewer follows only 3 accounts with 20 listens each, spread over two years of a 20,060-row visible timeline. p50 0.359 ms, p95 0.402 ms for 20 rows (the dense first page of this kind of read: p50 0.353 ms; scrobbles plan: SEARCH s USING INDEX scrobbles_owner_time (did=? AND (listened_at,uri)<(?,?)); USE TEMP B-TREE FOR ORDER BY). The same per-followee walks start below the cursor, so a deep page costs no more than a first page. Measured and reported, not asserted (Q10). (measured 0.36, threshold 0.35)
- `worst-global-hidden-newest-first`: Global feed, first page: the newest 1,000 rows belong to an owner deactivated by the production markInactive (rows kept, owner hidden), above a 20,060-row visible timeline. p50 0.745 ms, p95 0.793 ms for 20 rows (the dense first page of this kind of read: p50 0.232 ms; scrobbles plan: SCAN s USING INDEX scrobbles_global_time). The scrobbles_global_time walk visits and discards every hidden row above the first visible one, each with its owner-visibility probe, so the cost grows linearly with the hidden owner's newest rows. Candidate fixes (not decided): keep hidden owners' rows out of the global walk, for example by deleting them on deactivation and re-snapshotting on reactivation, or a visibility column in the global index. Measured and reported, not asserted (Q10). (measured 0.74, threshold 0.23)
