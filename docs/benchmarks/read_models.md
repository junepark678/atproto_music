## Rows-read budgets (ADR 0004 §15 Q10), page statement only

The budgets bound the production **page statement**'s cursor `rowsRead` at the default limit L = 20. They are hard assertions in `history/feed page statement rows read within ADR Q10 budgets`, derived from named constants in the suite. The rest of the call (the indexing-truth reads) is outside the budget. It appears only in the "Whole call" column, and the suite checks that it reads the same number of rows at every scale and depth.

| Read | Rule | Budget | Terms |
| --- | --- | --- | --- |
| History | L + 3 | 23 | L + 1 probe rows from `scrobbles_owner_time`, the owner's `users` row once (the visibility join), and on a deep page 1 keyset boundary row that the row-value seek on the DESC index steps over |
| Global feed | 2(L + 1) + 1 | 43 | L + 1 probe rows from `scrobbles_global_time`, each with one owner-visibility probe (a `users` row by primary key), plus 1 boundary row |
| Following feed (dense data) | 4(L + 1) + 1 + edges | 89 (4 visible edges) | the IN walk reads up to L + 1 rows from each followed account's `scrobbles_owner_time` range before the merge (4 dense followed accounts: 4(L + 1)), plus 1, plus the viewer's visible follow edges |

Met: all 12 history and feed page statements are within their budgets.

## Regressions this benchmark found (production fixes accepted by ADR 0004 §15 Q10)

W6-02 found two regressions and fixed them in `worker/src/do/read/history.ts` (W3-01) and `worker/src/do/read/stats.ts` (W3-02). ADR 0004 §15 Q10 (2026-10-25) **accepted** both fixes into W3-01/W3-02 ownership. Without them, deep pages read O(depth) rows and windowed statistics exceed their rows-read bounds. `worker/test/read/keyset.test.ts` covers the `keysetWhere` fallback, which keeps the anchor clause when `last > upper` or a key is non-ASCII.

- **Deep pages read O(depth) rows.** A cursor carries the traversal anchor (`upper`) and the last returned row (`last`). With both row-value bounds in the WHERE clause, SQLite used only the anchor as the index range start. It walked and filtered every row between the anchor and `last`: 5,023 rows read for a 20-row history page at depth 5,000. The fix: `keysetWhere` omits the anchor bound when `last <= upper`, which is true of every cursor the server issues. It selects the same rows, and history and both feeds share it.
- **Windowed statistics read the whole user.** The totals statement referenced the window CTE three times. Inlined, SQLite answered its DISTINCT/GROUP BY subqueries from the covering `scrobbles_stats` index searched by DID only, so a 7-day window of a 10,000-row user read 20,965 rows. The fix: `statsStatements` materializes the window for the totals statement of bounded windows, so rows read are proportional to the window. `all` keeps the inlined form, which already reads exactly the user's rows.

## Follow-ups

- `worst-following-sparse-followees-first`: Following feed, first page: the viewer follows only 3 accounts with 20 listens each, spread over two years of a 20,060-row visible timeline. The page statement read 92 rows for 20 returned (the dense-data Q10 budget of this kind of read is 88; index walk 62, visibility 30; scrobbles plan: SEARCH s USING INDEX scrobbles_owner_time (did=?); USE TEMP B-TREE FOR ORDER BY). SQLite walks each followee's scrobbles_owner_time range (up to L + 1 rows each) and merges the walks in a temporary B-tree, so rows read grow with the number of followees, not with the size of the global timeline. Measured and reported, not asserted (Q10). (measured 92, threshold 88)
- `worst-following-sparse-followees-deep`: Following feed, deep page (depth 30): the viewer follows only 3 accounts with 20 listens each, spread over two years of a 20,060-row visible timeline. The page statement read 70 rows for 20 returned (the dense-data Q10 budget of this kind of read is 88; index walk 32, visibility 38; scrobbles plan: SEARCH s USING INDEX scrobbles_owner_time (did=? AND (listened_at,uri)<(?,?)); USE TEMP B-TREE FOR ORDER BY). The same per-followee walks start below the cursor, so a deep page costs no more than a first page. Measured and reported, not asserted (Q10). (measured 70, threshold 88)
- `worst-global-hidden-newest-first`: Global feed, first page: the newest 1,000 rows belong to an owner deactivated by the production markInactive (rows kept, owner hidden), above a 20,060-row visible timeline. The page statement read 2,042 rows for 20 returned (the dense-data Q10 budget of this kind of read is 43; index walk 21, visibility 2,021; scrobbles plan: SCAN s USING INDEX scrobbles_global_time). The scrobbles_global_time walk visits and discards every hidden row above the first visible one, each with its owner-visibility probe, so rows read grow linearly with the hidden owner's newest rows. Candidate fixes (not decided): keep hidden owners' rows out of the global walk, for example by deleting them on deactivation and re-snapshotting on reactivation, or a visibility column in the global index. Measured and reported, not asserted (Q10). (measured 2042, threshold 43)
