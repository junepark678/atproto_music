# Rust-oracle goldens (W0-03)

Read-only inputs for the TypeScript rebuild (ADR 0004 §7.7, §10.4, §12). Every file in this
directory, apart from this README, is generated by calling the frozen Rust code in
`crates/*/src`. Nothing here is hand-edited. TypeScript tests must treat these files as the
oracle, while acceptance tests still hardcode the TESTING.md values.

## Provenance

- Oracle sources: `crates/core/src`, `crates/storage/src` and `crates/atproto/src` at commit
  `7ea7975f7e2ebfb53ea1f2c9e8e5275a60be5a00` (`feat/mvp-complete`). W0-03 adds the two
  examples below and does not modify any crate `src/` file. The commit that adds this
  directory records the exact generator source.
- Generated with cargo/rustc 1.99.0. The output depends only on the pinned crates in
  `Cargo.lock`, not on the toolchain version.
- Commands, run from the repository root:

  ```sh
  cargo run --locked -p atmusic-core   --example export_goldens     # core vectors
  cargo run --locked -p atmusic-atproto --example export_signed_cars # CARs, enumeration, stats, windows
  ```

  Each example accepts `-- --out DIR` (default `tests/goldens`). Each one renders everything
  twice in-process and refuses to write unless the two renders are byte-identical.
  `export_signed_cars` then reads every CAR back from disk and re-runs the Rust verifier
  against its manifest entry.
- Drift check: `bash scripts/check_goldens.sh`. It regenerates into a temporary directory and
  runs `diff -r` against this directory. It exits nonzero on any changed, missing or extra
  file. `--self-test` additionally proves that a one-byte mutation is detected.

## Test-only key material

All keys here are **fixed, public and test-only**. Never use them outside fixtures:

- Repository signing keys use the raw scalar `[0x07; 32]` for secp256k1 and for P-256, the same
  convention as `crates/atproto/tests/support/signed_repo.rs`. Their `did:key`s are listed in
  `signed_cars/manifest.json`.
- The fixture repository DIDs (`did:plc:aaaa…` and others) do not exist on the network.
- The cursor application keys are bytes `00..1f` ("primary") and `0x41 × 32` ("other"). The
  derived HMAC keys are listed in `cursors.json`.

## Notes for consumers

- **Lone surrogates.** `validation.json` stores each body as JSON text (`json`), so lone
  surrogates appear as `\uD800`-style escapes. Rust's JSON decoder refuses such documents
  (`stage: "json"`), so no Rust string can hold one. A TypeScript validator receives them after
  `JSON.parse` and must reject them.
- **Error codes.** Every Rust `ValidationError` uses code `invalid_field`, plus the field name.
  The TypeScript reason codes map onto those fields.
- **CommitMismatch.** Rust has a single `CommitMismatch` error. The manifest's `corruption`
  field tells `did_mismatch`, `bad_version` and `bad_rev` apart.
- **`record_cid_swap`.** The CAR carries a correctly hashed but different record block in place
  of the CID that the signed MST commits to. The proven CID therefore has no block in the CAR,
  which a verifier cannot tell apart from a missing record block plus an unreferenced extra
  block. Rust reports `MissingProof`, and the TypeScript code is `missing_block` (ADR 0004 §7.3
  step 3: an incomplete path throws `missing_block`). `record_cid_mismatch` cannot be produced
  from a CAR, because only CID-verified blocks enter the proof store. W2-03 covers it with its
  own unit case (`record-proof.test.ts`), not with a golden CAR.
- **Rev syntax.** Rust checks TID syntax only in `verify_snapshot`, so the corruptions are applied
  to the full-repo CAR. They all touch the commit, the MST root node or the r01 record, which
  keeps them on the r01 proof path.
- **Oversize CARs.** The oversize CARs are 8 MiB + 1 byte, one byte over the Rust
  `MAX_CAR_BYTES`. The extra bytes are a zero-filled padding block, so they compress to almost
  nothing in git.
- **atrium-repo 0.1.8 MST insertion bug.** Inserting the 59 repository records in fixture order
  silently dropped 3 entries (r01, r02 and the follow). The exporter therefore inserts in key
  order. It then asserts that the tree enumerates exactly the inserted records, and that reverse
  insertion order gives the identical MST root. Rust test helpers that insert many records in
  arbitrary order may be affected. The production verifier only reads trees.
- **Independent check.** At generation time the CARs were also checked once with `@atcute/car`,
  `@atcute/mst` and `@atcute/crypto` (the ADR §4.5 pins). The results matched:
  - every valid signature verifies, and both corrupted signatures (byte flip and high-S) fail;
  - rebuilding the MST from its leaves reproduces the signed root;
  - `findRpathAndBuildProof` returns the r01 CID from the inclusion proof and `null` from the
    exclusion proof;
  - the music leaves equal `snapshot_enumeration.json`.

  That check is not part of `check_goldens.sh`, because W2-03 and W3-05 own the TypeScript
  side.
